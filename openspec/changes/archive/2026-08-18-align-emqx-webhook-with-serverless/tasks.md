## 1. 前置驗證與分支判定

- [x] 1.1 依「以 Dashboard 建立閘門選定分支 B，部署後再驗證週期性 health check」決策,記錄已完成的 Dashboard spike 並正式選定分支 B:HTTP Server connector 對現有 ingestion origin 執行 connectivity test 時因根路徑 404 失敗,且 `New` 按鈕維持 disabled,因此無法先建立 connector 觀察週期性 health check。完成時 deploy/development/EMQX_RUNBOOK.md 的判定小節 SHALL 記錄觀察日期、sanitized connector 建立閘門結果、分支 B 決策與「未建立 connector、未傳送 secret」的邊界。驗證方式為內容審閱,確認紀錄不含帳號、secret、Authorization header、事件 payload 或 Firestore document data。此任務提供 Broker-reachable health surface 的前置判定證據,且必須在其他 implementation tasks 前完成。
- [x] 1.2 先寫測試再實作已選定的分支 B,使 Broker-reachable health surface 明確成立:ingestion origin 的 `GET /` 回傳 `200 {"status":"ok"}` 與非空 `x-request-id`,不要求認證;`POST /`、`PUT /`、`PATCH /`、`DELETE /` 與 `HEAD /` 仍回 sanitized `404 not_found`,既有 `/health`、`/healthz` 與 `/v1/emqx/events` 行為不變。驗證方式為 services/ingestion-api/test/app.test.ts 先新增會失敗的根路徑 GET 測試與非 GET 表格驅動測試,再於 services/ingestion-api/src/app.ts 沿用既有 health handler 並停用自動 HEAD route,最後執行 `npm --prefix services/ingestion-api run check` 全數通過。
- [x] 1.3 ingest 部署後的 Dashboard 與 Cloud Run request metadata 實證並補齊 Serverless connectivity contract:Dashboard `Test` 實際對 connector origin 發出 `POST /`,且帶 `content-type: application/json` 的空 body 在既有 parser/error handler 下回 500。先寫測試再讓 `POST /` 與 `GET /` 共用 sanitized health handler,其中空 JSON body 的精確 `POST /` 亦回 `200 {"status":"ok"}` 與非空 `x-request-id`;`PUT /`、`PATCH /`、`DELETE /` 與 `HEAD /` 仍回 `404 not_found`,`/v1/emqx/events` 的 parser、認證與狀態碼完全不變。驗證方式為 app.test.ts 先重現 EMQX 的空 JSON `POST /` 500,再於實作後執行完整 ingestion check。
- [x] 1.4 依「以 Action body credential wrapper 取代 Serverless 不持久化的 custom headers」決策,先寫測試再擴充 ingestion `/v1/emqx/events`:既有有效 Authorization header + raw envelope 行為維持不變;無 header 時只接受恰含 `webhookAuthorization` 與 `event` 的 wrapper,以相同 current/optional previous secret constant-time 驗證後只把 inner event 送入既有 validator 與 sink。缺漏或錯誤 credential、額外 top-level 欄位、event 非 plain object、同時使用 header/body credential 全部回 sanitized 401 `unauthorized` 且 sink 零呼叫。驗證方式為 services/ingestion-api/test/app.test.ts 先新增上述有效與拒絕 cases 並確認失敗,再實作後執行 `npm --prefix services/ingestion-api run check`;測試名稱、error body 與工具輸出不得含 secret 或完整 request body。此任務交付 Contract webhook envelope 與 Referenced Bearer secret 的 Serverless transport,且不得改 topic、inner envelope、payload schema、eventId 或 Firestore model。
- [x] 1.5 部署並驗收補齊後的分支 B:以 `npm run ingestion:development:deploy` 部署已通過 check 與 runtime image smoke test 的 immutable ingestion revision,再執行可重複的既有 development ingestion verification;Dashboard connector SHALL 使用 HTTPS/TLS enabled、因無 CA bundle 欄位而將 `TLS Verify` 記為 disabled 平台例外,connectivity test 成功並使 `New` 可用。action body SHALL 精確使用 `{ "webhookAuthorization": "Bearer {{PEECARE_EMQX_WEBHOOK_SECRET_CURRENT}}", "event": ${.} }`,不得依賴不持久化的 custom headers。建立 connector、rule 與 action後,對 canonical urination topic 發送一筆唯一 probe,確認 connector 在至少一個 `health_check_interval` 後仍顯示 connected 且 Firestore 恰有一份對應事件文件。驗證方式為將 sanitized revision identity、Dashboard connected 狀態、body credential transport、TLS Verify 平台例外、probe 落地結果與觀察時間記入 deploy/development/EMQX_RUNBOOK.md;紀錄與工具輸出不得含 secret 值、Authorization header、body credential、事件 payload 或 Firestore document data。

## 2. 設定工具改寫

- [x] 2.1 先寫測試再實作,使設定工具滿足 Serverless management API capability boundary:工具執行後不再請求 API specification 文件,也不再對 connector、action、rule 任一端點發出請求。完成時可觀察的結果是工具在僅開放 client、subscription 與 publish 端點的部署上能正常執行完畢。驗證方式為在 deploy/development/configure-emqx-webhook.spec.ts 以注入的假 adapter 斷言請求路徑集合不含 api-spec、connectors、actions、rules,測試先失敗後通過。
- [x] 2.2 以環境變數提供平台產生的 connector 與 action 識別名稱,滿足 Configurable platform-assigned integration identity:工具接受任何有界且不含空白、換行與 null 字元的識別名稱,不再要求等於特定字串,並在名稱為空或含換行時於任何網路請求之前失敗。驗證方式為在 configure-emqx-webhook.spec.ts 新增表格驅動測試,涵蓋 c-d1f775fd-efa39d 形式、operator 自訂形式、空字串與含換行字元四種輸入的接受與拒絕結果。
- [x] 2.3 將核准 delivery policy 縮減為 Serverless 可設子集,滿足改寫後的 Approved retry policy:工具只約束 connector 層的 pool_size、enable_pipelining、connect_timeout 與 health_check_interval 四項,將 action 層的 query_mode、worker_pool_size、inflight_window、max_buffer_bytes、request_ttl 記錄為平台預設而不加約束,並在偵測到 retry_interval 時拒絕。同步調整 deploy/development/emqx-webhook.template.json,使其承載的核准值與上述子集一致,移除無法持久化的 action headers,將 action body 改為固定 `webhookAuthorization` + `event` wrapper,並記錄 HTTPS/TLS enabled 與 `TLS Verify: disabled` 平台例外。驗證方式為 configure-emqx-webhook.spec.ts 斷言 pool_size 為 16 時回報 unapproved_delivery_policy 且零 mutation、action 層欄位缺漏時不觸發失敗、範本不含 Authorization/custom header、body wrapper 只有兩個 top-level 欄位,以及核准值集合剛好是 connector 四項。
- [x] 2.4 將 Data Integration 設定改為 Dashboard 人工建立加檢查表,滿足 Console-managed integration with auditable checklist:工具改為輸出一份 sanitized 檢查表摘要,涵蓋其約束的每個 console 欄位、標明 console 未暴露因而不受約束的欄位,指名 ingestion 部署實際使用的 Secret Manager secret 與 numeric version reference,並以 reference token 顯示固定 body wrapper 而非 custom header。摘要 SHALL 記錄 HTTPS/TLS enabled 與 `TLS Verify: disabled` 平台例外,且不含 secret 值。移除 apply 寫入模式,或使其以明確錯誤碼拒絕並說明部署不支援 API 寫入。驗證方式為執行 dry-run 後以 grep 確認輸出不含 secret 值、確認退出碼為零,並由 spec 測試斷言零寫入請求。
- [x] 2.5 新增 deploy/development/emqx-serverless-console-checklist.md,提供逐欄位的 Dashboard 預期值對照,涵蓋 connector、rule SQL 與 action 三部分,明確標示 console 未暴露的欄位、custom headers 不持久化、固定 body credential wrapper,以及 HTTPS/TLS enabled 但 `TLS Verify` disabled 的平台例外。完成時可觀察的結果是操作者能單憑此文件在 Dashboard 核對設定而不需閱讀腳本原始碼。驗證方式為內容審閱:逐項比對文件所列欄位與 2.3 所定核准值一致,wrapper 只含 reference token 而不含任何 secret 值,且沒有指示操作者把 credential 放進 URL 或 custom header。

## 3. 驗證腳本改寫

- [x] 3.1 [P] 沿用 adapter 注入模式改寫驗證腳本:將發送 probe 與讀取 Firestore 事件文件兩類外部依賴抽象為注入的 adapter 方法,使核心驗證邏輯不直接建立網路連線或 Firestore 連線。完成時可觀察的結果是驗證邏輯能在完全不接觸真實 broker 與 Firestore 的情況下被測試。驗證方式為 deploy/development/verify-emqx-webhook.spec.ts 以假 adapter 驅動全部驗證路徑,測試執行過程中無任何真實對外請求。
- [x] 3.2 以 Message Publish API 加 Firestore 查詢取代 action metrics 驗證,滿足改寫後的 Webhook delivery verification:腳本依序對 canonical urination topic 與 canonical battery topic 發送 probe 並各自確認 Firestore 出現剛好一份對應事件文件,再對精確 legacy prototype topic `peecare/device/1/status` 發送 probe 並確認 Firestore 未出現對應文件,最後輸出不含 secret 值與事件 payload 的 sanitized 摘要。legacy absence 只判為端到端未落庫,不得宣稱直接證明 broker rule 排除。驗證方式為 verify-emqx-webhook.spec.ts 斷言四種情境:兩個 canonical topic 各得一份文件判為 delivered、legacy topic 無文件判為 legacy non-delivery satisfied、canonical topic 在有界輪詢後仍無文件判為 delivery failure。
- [x] 3.3 為 secret rotation 演練加入明確的前置條件檢查,滿足 Webhook delivery verification 對雙 secret 的要求:當 ingestion 部署只接受單一 secret 版本時,腳本回報未滿足的前置條件且不將 rotation 判為已驗證,而非直接以 invalid_rotation_references 中止而不說明原因。驗證方式為 verify-emqx-webhook.spec.ts 斷言單一版本情境下輸出前置條件未滿足的錯誤碼,且 rotation 結果不為 verified。
- [x] 3.4 依「以真實 MQTT 裝置身分加 Firestore 查詢取代 action metrics 驗證」決策,ingest live 422 實證並修正 synthetic publisher 假設:保留已完成的 adapter 核心與 Firestore polling,將 live `publishProbe` 從 Serverless Message Publish API 改為 inventory 中既有 development device 的 strict-TLS MQTT 5 publisher。CLI SHALL 從 hidden interactive TTY 讀取 device password,拒絕 argv/environment/file credential,且不再要求 Deployment API key/secret；canonical probe 必須以 inventory deviceId/client principal、QoS 1、retained false取得成功 PUBACK,legacy attempt 可由 ACL 拒絕或以 Firestore absence判為未交付。先新增測試重現 Message Publish 即使帶 deprecated clientid 仍不能作為 publisher-binding 證據,再測 MQTT adapter identity、PUBACK/ACL rejection、hidden-TTY precondition與 sanitized output；不得放寬 rule SQL 或 ingestion publisher_mismatch 契約。
